# Формы и заявки

Реализованный локальный модуль. Основа — собственный небольшой конструктор и
готовые компоненты Mantine. RJSF и платные конструкторы не устанавливались.

## Сценарий

1. Администратор открывает **Forms**, создаёт шаблон, задаёт название и описание
   ситуации, в которой агент должен предложить форму. Поля добавляются, удаляются
   и переставляются; есть предварительный просмотр.
2. В **Agents → Edit agent → Available forms** назначает агенту шаблоны.
3. Клиент разговаривает или пишет агенту. Агент открывает форму и сразу сохраняет
   известные поля, даже если известно только имя. Не требуется ждать остальных
   обязательных данных. Недостающие сведения запрашиваются последовательно.
4. Форма находится в отдельной панели справа. На телефоне переключаются
   кнопкой с иконкой боковой панели в шапке; сессия и голос сохраняются, доступны управление
   микрофоном и переключение режима. Лента сообщений не прокручивает форму.
5. Ручной ввод автоматически сохраняется через 600 мс после паузы или при выходе
   из поля, даже если остальные обязательные поля ещё пусты. **Save draft** остаётся
   для немедленного сохранения и повтора после ошибки. Зелёная галочка появляется
   только после подтверждения сервера; ожидание, сохранение и ошибка различаются.
   Отправка сообщения, закрытие беседы, смена режима и создание ссылки на разговор
   сначала дожидаются сохранения формы. Переход к другой заявке недоступен, пока
   остались правки. При перезагрузке с несохранёнными данными браузер запрашивает
   подтверждение ухода; после успешного сохранения данные восстанавливаются с сервера.
6. Клиент проверяет данные, отмечает подтверждение и нажимает **Submit request**.
   Агент не имеет инструмента отправки от имени пользователя.
7. Сотрудник открывает **Requests**, просматривает ответы/фото и меняет статус:
   **New → In progress → Waiting for customer → Closed**. Разрешены обратные
   переходы между этими статусами. История сохраняет автора и время изменения.
8. Клиент видит сохранённые черновики и отправленные заявки в **My requests**.
   После отправки ответы не редактируются; клиент может следить за статусом.

## Поля и файлы

Поддерживаются короткий/длинный текст, email, число, дата, выбор, чекбокс, фотографии.
Не более 30 полей. У каждого поля постоянный ID, подпись, тип, обязательность;
у выбора — варианты. Текстовые значения ограничены 4000 символами.

JPEG, PNG, WebP: до 5 фотографий на поле, 20 на заявку, 8 MB и 20 мегапикселей на
исходный файл. Сервер декодирует изображение, исправляет ориентацию, уменьшает до
2400 пикселей, сохраняет JPEG без исходных метаданных. Поддержаны превью, состояние
загрузки и удаление фотографии из черновика. Повтор загрузки — повторный выбор
файла. HEIC не поддерживается, анализ содержимого фотографии моделью не добавлен.

Файлы находятся в закрытом SeaweedFS; API проверяет доступ перед выдачей изображения.
Метаданные хранятся в Postgres. Отсоединённые от черновика объекты сохраняются
согласно текущей политике хранения, но недоступны через заявку.

## Данные и доступ

- Шаблон принадлежит организации. Сервер проверяет назначение формы агенту.
- Заявка содержит неизменяемый снимок формы и её версии, ответы, вложения,
  организацию, разговор, пользователя/гостя, статус и историю статусов.
- Черновик сохраняет только известные значения. Полная обязательность проверяется
  при отправке. Изменения и отправка проверяют ревизию; повторная отправка
  идемпотентна. Другие сотрудники могут одновременно работать со статусами.
- При конфликте с агентом ручные несохранённые значения остаются на экране:
  пользователь выбирает свои либо сохранённые. Агент по умолчанию не заменяет
  уже заполненные другим значением поля. По явной просьбе клиента агент может
  исправить выбранные поля: передаёт старые значения вместе с новыми, сервер
  проверяет ревизию. При изменении данных другим участником устаревшая правка
  отклоняется. Остальные поля сохраняются; ручное исправление также доступно.
- Гостевой секрет генерирует сервер; виджет хранит его в localStorage сайта-хозяина
  отдельно для каждой публикации. Сервер хранит хеш. Секрет восстанавливает доступ
  к заявкам при следующей сессии этого же виджета. При очистке хранилища доступ
  теряется; серверные записи не удаляются. Если браузер запрещает localStorage,
  доступ остаётся только в текущей сессии.
- Сотрудники видят отправленные заявки своей организации. Гости — только свои.
  История запросов в текущем интерфейсе ограничена 200 последними записями.
- Виджет хранит conversation ID рядом с гостевым секретом. При повторном открытии
  или перезагрузке продолжается тот же разговор: история загружается в интерфейс
  и контекст модели. ID без секрета не даёт доступа. В кабинете сотрудника по умолчанию
  продолжается его последний разговор с выбранным агентом.
- Выбранная в **My requests** заявка становится активной на сервере. Агент получает
  её поля, ответы и статус перед ответом и заполняет именно её. Можно выбрать свой
  черновик из предыдущего разговора; исходная связь с разговором сохраняется.
  Повторное открытие восстанавливает выбор. Устаревшая запись агента после смены
  выбранной заявки отклоняется. Отправленная активная заявка остаётся только для
  просмотра: агент не создаёт вместо неё новый черновик. Новый запрос можно явно
  начать кнопкой **Open form**.
- Постоянный разговор отделён от подключения LiveKit: при возвращении создаётся
  новая комната/run ID, предыдущее подключение закрывается. Позднее событие завершения
  старого воркера не закрывает новый сеанс; старый воркер не может менять заявки.
  Одновременное открытие нескольких вкладок заменяет предыдущее подключение.
- Обновления панели опрашиваются раз в две секунды; это не поток по каждому символу.
  Ручные изменения отправляются отдельно, частичными последовательными запросами.
  Поля остаются доступны во время автосохранения: более ранний ответ сервера не
  стирает последующий ввод. Конфликт ревизии из-за другого поля автоматически
  повторяется с актуальной ревизией; изменение того же поля требует выбора
  пользователя. Ошибка сохраняет ввод на экране и блокирует отправку сообщения,
  пока черновик не сохранён. Окончательная отправка заявки по-прежнему требует
  отдельного подтверждения пользователя.

## Реализация и контракты

Миграции `002_forms.sql` и `003_conversation_resume.sql`; серверные модули `forms`, `requests`, `request_domain`,
`request_files`, `form_schemas`, `active_request`; агентные инструменты в `form_tools.py`.
Форма — ограниченная декларативная JSON-конфигурация с версией, без скриптов.
Pydantic проверяет данные на сервере; JSON Schema/OpenAPI генерируют типы клиента.
Клиентские компоненты находятся в `apps/web/components/forms`.

Seed создаёт **Repair request** и назначает Emma только при первом создании
демо-формы. Изменённые пользователем назначения не перезаписываются.

Проверки: реальные Postgres/S3-тесты доступа, валидации, ревизий, снимков, вложений,
повторной отправки и статусов; тесты агентных инструментов; браузерный сценарий
с настоящим Mistral, пошаговым заполнением, фото, отправкой, возвратом гостя и
обработкой сотрудником; мобильные проверки Chromium/WebKit; синтетическая речь
через LiveKit/STT с проверкой сохранённых полей. Это не тесты на физических телефонах.

## Следующие этапы

Почтовая отправка ссылок, вход по ссылке с другого устройства, HEIC, анализ фото,
автоматические назначения ответственным, уведомления, расширенные процессы и
условия форм. Эти возможности не заявляются готовыми.

## Результаты проверки этой реализации

14 API-тестов, 8 тестов воркера, 4 UI-проверки и 19 браузерных сценариев прошли.
TypeScript и Pyright — без ошибок. Синтетический английский голосовой сценарий
сохранил имя и описание в черновик; первое ответное аудио — примерно через 5 секунд
после окончания фразы в этом прогоне. Это измерение одного прогона, не SLA.
Отчёты и снимки находятся в `artifacts/forms`.

### Восстановление разговора и активной заявки

Проверка вручную: открыть виджет, назвать имя и попросить форму, закрыть виджет,
перезагрузить страницу и открыть его снова. Должны сохраниться история, имя и
выбранная заявка. Уточнение следующего поля должно дополнить тот же черновик.
В **All requests** можно выбрать другую заявку; агент работает с новым выбором.
Отправленная заявка остаётся неизменяемой. Для нового обращения клиент выбирает
шаблон и нажимает **Open form**.

Регрессии покрывают восстановление приватной и гостевой переписки, доступ по
гостевому секрету, выбор старого черновика, отклонение записи в неактивную заявку,
защиту нового подключения от завершения старого, приватность контекста формы,
реальное продолжение разговора моделью и возврат в мобильный виджет.

После добавления восстановления прошли 18 API-тестов, 9 тестов воркера,
4 UI-теста и 20 браузерных сценариев. В том числе реальный Mistral вспомнил
сведения после перезагрузки и заполнил выбранный второй черновик, не изменяя
первую отправленную заявку. Мобильное восстановление проверено в Chromium и
WebKit. TypeScript и Pyright — без ошибок. Отчёты: `artifacts/resume`.

### Исправление заполненных полей агентом

Клиент может попросить: «Исправь Donkerstrasse 77 на Dunkerstrasse 77».
`fill_form` принимает `previous_values` для явно запрошенных замен, сверяет их
с текущим черновиком и отправляет частичное изменение с его ревизией. Без старого
значения автоматическая перезапись заполненного поля по-прежнему отклоняется.
Агент подтверждает исправление только после успешного сохранения.

Исправления адреса на английском и немецком проверены настоящим Mistral в виджете:
ID заявки, имя и email сохранились. Тесты также проверяют отклонение устаревшей
замены, включая поле, которое пользователь уже очистил. Отчёты —
`artifacts/corrections`.

### Автосохранение ручного ввода

Контроллер `apps/web/lib/draftAutosave.ts` последовательно сохраняет частичные
изменения и обрабатывает конфликты. `useDraftAutosave` подключает задержку 600 мс,
состояния полей и предупреждение браузера об уходе с несохранёнными правками.
Новая отправка сообщения сначала дожидается сохранения, чтобы модель получила
актуальные ответы активной заявки.

Проверены задержанный ответ сервера во время ввода, конфликт ревизий, отказ
сервера и повтор, восстановление того же черновика на десктопе и мобильном
экране. Настоящая модель прочитала имя, введённое вручную. Проверки форм в
Chromium/WebKit прошли; полный модельный сценарий с фото потребовал повторного
запуска из-за отказа модели открыть форму в первом прогоне. Отчёты и скриншоты:
`artifacts/autosave`.

### Короткие номера и удаление черновиков

Каждая заявка, включая существующие записи, имеет постоянный `code`:
`A01`…`A99`, `B01`…`Z99`, затем `AA01`. Номера уникальны внутри
организации. Атомарный счётчик и ограничение уникальности защищают параллельное
создание; удалённые номера не выдаются снова. Номер виден клиенту и сотрудникам
в заголовке и списках; списки можно фильтровать по номеру или имени формы
среди загруженных заявок. Инструменты агента возвращают `request_code`, а
инструкция требует использовать его при обсуждении заявки. UUID остаётся
внутренним идентификатором и не заменяется номером в проверках доступа.

Удаление доступно пользователю только для черновиков через подтверждение
`delete-request=<id>`. Перед открытием подтверждения ручные правки сохраняются.
DELETE проверяет принадлежность и статус под блокировкой. Отправленные заявки
защищены ответом 409. Удаление снимает активный выбор во всех разговорах и
исключает черновик из API, инструментов агента и доступа к фотографиям.
Техническая запись с `deleted_at` и объекты хранилища сохраняются согласно
текущей политике хранения; пользовательского восстановления нет.

Проверки: 29 API-тестов, 11 тестов воркера, 15 UI unit-тестов, браузерное удаление
с восстановлением подтверждения на 1440/390 px и открытие заявки в админке.
TypeScript и Pyright проходят. Отчёты: `artifacts/request-codes`.
